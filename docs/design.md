# WeCom Inbox：产品与实施计划

更新：2026-10-23。状态：第一版候选代码已完成并进入私有验收；真实平台收件测试待完成。
依据：项目所有者要求独立、有外部使用价值，并可与现有 Agent 系统互补；
2026-10-23 GitHub 同类项目调研；现有代码基线 `2569cab`。
本计划扩展现有网关，未勾选的内容是待实现或待验证事项，不能一律理解为功能缺失。

## 产品决定

**定位：面向业务资料的自托管企业微信收件箱。** 使用者用自己的机器人接收消息和附件，
保存来源、查询和导出资料，再选择交给业务程序、知识库或 Agent 处理。
首批用户是已有企业微信机器人、需要处理业务资料的团队；外部需求强度尚待真实试用验证。

| 决定 | 选定方案及理由 |
|---|---|
| 名称 | `WeCom Inbox`；拟发布仓库 `iCookCloud/wecom-inbox`，比原名更能表达业务收件用途。已创建私有仓库 |
| 核心独立性 | 收件、归档、检索、导出无需模型、特定 Agent、内部账号或内部服务器 |
| 与 Agent 系统的关系 | 核心提供版本化 HTTP API、Webhook 和 CLI；特定系统只编写 Adapter，不修改核心业务模型 |
| 实现基础 | 优先沿用现有 Go 收取程序；单进程、单机 SQLite 和本地附件目录，Web 静态资源内嵌。SQLite 驱动已固定为 modernc.org/sqlite v1.61.0，并验证无 CGO 构建 |
| 许可证 | 公开版选 MIT，发布前核对源代码归属和第三方许可，保留必要声明；本计划本身不变更历史代码许可 |
| 仓库路径 | 从核对后的源文件建立独立发布仓库，先准备私有版本，再公开合格版本；原内部仓库和运行数据独立保留 |
| 兼容 | 现有 `wecom-gw`、配置和 JSONL 有迁移路径；首版旧格式只读导入，保留原件和时间、来源，不原地重写 |
| 记录维护 | 本文是计划真源，README 标示已实现范围；后续直接更新本文，不另建任务总结文档 |

## 已有实现与差距

已有：多 Bot 长连接、配置热加载、媒体下载解密、JSONL 查询、单实例文件锁和落地后回执。
README 记载的 2026-07 实测属于历史证据；本次规划没有重跑真实机器人测试。

首版新增：持久入站队列、消息去重、附件一对多模型、SQLite 检索、Web 界面、鉴权 API、
独立订阅投递状态、结果回传、自动化测试和候选版发布材料。当前测试套件位于 `tests/`，MIT 许可证和第三方声明已经加入仓库。
旧实现下载完成后才追加流水；新版本先持久记录入站事件，再调度附件处理，并用恢复清单协调文件与数据库提交。

## 同类项目依据与差异假设

| 项目 | 已证实的重合 | 对本项目的约束 |
|---|---|---|
| [fyaic/wecom-agent-gateway](https://github.com/fyaic/wecom-agent-gateway) | 独立 Agent 网关、多个 Adapter、持久投递、去重与恢复 | 不以“通用 Agent 接入”作为创新点；其[入站媒体生命周期](https://github.com/fyaic/wecom-agent-gateway/blob/3c5e83006569b5318aeb0ab74f86e2e9bda0c680/docs/adr/0007-ephemeral-media-boundary.md)为任务临时文件，业务资料长期保存是本项目重点 |
| [官方 OpenClaw 插件](https://github.com/WecomTeam/wecom-openclaw-plugin) | 多账号、媒体消息、访问控制和工具 | 不再造一个绑定 OpenClaw 的完整 AI 平台 |
| [ClawRelay](https://github.com/wxkingstar/clawrelay-wecom-server) | 多 Bot、JSONL 日志、Claude Code 中转 | 多机器人和日志本身不构成差异 |
| [wecom-archive](https://github.com/TorbenXiong/wecom-archive) | Windows 数据归档、搜索、附件、导出 | 对照其资料查找体验；本项目只处理机器人实际收到的内容，不采集桌面全量聊天 |
| [Obsidian Gateway](https://github.com/huang5307/wecom-obsidian-gateway) | 微信客服到 Obsidian 的资料归档 | 不把业务记录绑定某个知识库或目录约定 |

差异是假设，不是市场空白结论：长期资料、无模型独立使用、多个消费者各自处理同一资料、
失败可见且可重试，形成一个易部署的整体。开发时用相同资料集比较已有方案；
若已有方案完整满足验收，优先复用或贡献，不为另起仓库重复实现。

## 首版范围

1. 多 Bot 接收；保存机器人、会话、发送人、平台消息 ID、收到时间与平台时间（若存在）。
2. 附件长期保存，保留原文件名与来源；支持一条消息的多个附件、引用与图文混排。
3. Web 收件箱：机器人状态、资料列表、时间/发送人/类型筛选、正文与文件名检索、详情、附件下载、失败状态。
4. 分页 HTTP API、CLI 查询、JSON/CSV 导出；导出可供外部程序使用，不含凭据和内部绝对路径。
5. Webhook 订阅：每个消费者独立状态、签名、确认、有限重试、失败队列与手动重放。
6. 处理结果登记和回复到已授权的原会话；“已收件”与“处理完成”分别表达。
7. 安装包、配置模板、备份恢复说明、中英文 README、MIT、贡献指引、问题模板、CI 与版本发布。

本版不包含：模型托管、多 Agent 编排、向量知识库、业务审批引擎、SaaS 计费、多主机高可用、
任意个人微信/外部群全量采集。首版不提供资料自动删除；以后引入保留策略时需有明确配置和可预览的删除流程。
平台接收/发送限制必须经专用测试 Bot 验证后写入能力表，不用其他项目的宣传替代验证。

## 数据与接口边界

流程：平台回调 → 校验与持久入站 → 附件保存 → 收件确认 → 查询/导出/订阅 → 消费者处理 → 结果与可选回复。

- `messages`：以 `(bot_id, platform_message_id)` 去重，使用不可变内部 ID；缺平台 ID 的事件需独立规则，不能随意合并。
- `attachments`：一对多关联消息，记录状态、大小、哈希、原文件名与受控存储键；使用暂存写入和原子提交。
- `consumers/subscriptions/deliveries/results`：每消费者独立关联资料；投递成功仅表示接收确认，不表示业务处理完成。
- SQLite 是新运行状态真源；原 JSONL 是只读迁移输入和可选导出，不同时维护两个可写真源。
- HTTP API 从 `/v1` 起，使用稳定 ID、游标分页与结构化错误；凭据按 Bot 范围授权，读资料和发回复分权。
- Webhook 提供稳定事件 ID、HMAC 签名和重试次数，采用 at-least-once；消费者按事件 ID 幂等处理，不承诺 exactly-once。
- 回传结果以消费者和事件 ID 幂等登记；发往平台的回复单独记投递状态，超时结果不明时显示“不确定”，不伪报成功。
- 首版一个服务拥有 Bot 连接。Agent 适配器通过网关接口消费，不再为同一个 Bot 建第二条长连接。
- UI 使用受保护会话及写入校验；API 使用独立令牌，默认监听本机。配置、数据库和附件限制本机文件权限。
- API/导出/普通日志不暴露 Bot secret、媒体 AES key 或临时签名 URL；旧 JSONL 的 raw 可能含后两者，不能直接公开导出。

## 失败与恢复约定

| 失败 | 恢复行为 | 用户看到的结果 |
|---|---|---|
| 下载中断或签名 URL 过期 | 有效期内有限重试；过期保留记录并请求重发，不保证可以重新下载 | 附件失败及原因，消息仍可查 |
| 文件落盘成功、数据库提交失败 | 私有暂存和幂等协调；不发成功回执；重启可恢复或明确挂起 | 待恢复，不出现虚假的完整附件 |
| 磁盘满、数据库不可写 | 停止接收后的成功确认，记录健康异常；处理有界，恢复后继续 | 服务异常，已提交数据可保留 |
| 重复回调或消费者超时 | 稳定 ID 去重；投递允许重试，业务方确认幂等 | 每消费者独立状态，不重复创建资料 |
| Webhook 目的端持续失败 | 有限指数退避后进入失败队列，人工重放；目的地址受管理员配置和网络范围限制 | 可定位失败并重试 |
| 平台回复超时、结果不明 | 保留“不确定”状态与回执线索，避免宣称恰好发送一次 | 区分已登记、已发送、发送不确定 |
| 配置更新无效或同 Bot 抢线 | 拒绝坏配置并沿用原配置；重复实例拒绝，跨主机抢线明确告警 | 原服务尽量继续，显示原因 |
| 数据迁移不兼容或备份恢复失败 | 在副本验证；禁止覆盖旧数据；给出恢复步骤 | 旧资料仍可回退使用 |

边界测试同时覆盖：同名文件、多附件、重复提交、分页期间新增消息、零结果、部分附件失败、
消费者迟到确认、重启后凭据失效、超大输入和未授权下载。具体上限在 U1 固定并在配置文档公开。

## 离线基线补验与剩余事项

- 旧网关只读 CLI 与新版导入使用同一组 5 行合成 JSONL（含 1 行重复、1 个缺失附件）：旧 CLI 返回 5 行；新版保留 4 条唯一消息，报告 1 次去重、1 个失败附件，2 个有效附件保存并校验。原始 JSONL 未改变，没有机器人或外部网络调用。
- Linux 原生安装、空 Bot 配置、HTTP 启动、样例导入和备份恢复已通过新增 CLI smoke 检查。
- macOS 15 arm64 原生 runner 已通过全部 Go/race 检查及 CLI 安装、无 Bot HTTP 启动、导入和备份恢复。最初的失败已定位为 Python HTTPServer 启动等待反向 DNS；示例现使用实际绑定地址，回归测试会拒绝反向 DNS 以确认没有隐藏依赖。验证记录：[GitHub Actions 40046423025](https://github.com/iCookCloud/wecom-inbox/actions/runs/40046423025)。这不等于真实企业微信收发或真人 Mac 桌面验收。
- 尚未完成：断线重连与白名单外拒收的真机验证、未参与开发者的独立上手、自研 Agent 专有协议适配、正式公开版和资助申请。专有 Agent 适配不阻塞独立版发布。
- 社区同类程序目前做的是文档与源码对照，没有声称逐一部署完成或完成性能排名。

## 真实平台验收记录（2026-10-24）

专用测试 Bot（API 模式、长连接），只授权"发送消息"与默认的"获取对话用户 userid"，其余文档/邮件/日程等权限代码未使用、未授权。
对外汇报版见 [acceptance-report-2026-10-24.md](acceptance-report-2026-10-24.md)。测试人员在企业微信单聊和测试群中发送；服务端用 `/v1` API 下载每个附件，核对大小、SHA-256 与文件类型。

| 场景 | 结果 |
|---|---|
| 单聊文字、图片、PDF、Excel | 通过；原件一致，客户端收到"已归档"回执 |
| 群聊 @机器人 文字 | 通过；不 @ 的群消息平台不推送 |
| 群聊引用新发的图片/文件（原消息未 @ 机器人） | 通过；原件以 `quoted_image`/`quoted_file` 保存 |
| 引用过期文件 | 平台只给文字"资源已过期或者被封禁"，无原件 |
| 合并聊天记录（引用或单聊转发） | 平台不支持：引用时只给"[该消息类型暂不能展示]"；转发时平台自动回复"目前不支持理解此类型消息"，不推送给程序 |
| 语音（单聊或引用） | 平台只给转写文字，不提供录音文件 |
| 图文混排（单聊、群聊 @、引用） | 通过；一条只含一张图，多张图由客户端拆成多条消息分别入库 |
| 视频 | 手机相册发送为 `video` 类型；电脑端或文件按钮发送为 `file` 类型；原件均完整 |
| 54 MB zip | 平台会推送，本程序按 `max_file_mb` 上限拒收；文件名因未下载而记为 `file` |
| 处理结果回复原群（距最后一次 @ 约 2.5 小时） | 平台确认送达；作为普通群消息发出，不引用原消息、不 @ 发送人，回复内容需自行写明对应的人和文件 |
| 回复中 @ 成员（`<@userid>`、`@userid`、`@显示名`） | 均不生效，原样显示；官方长连接文档的 markdown/template_card 均无 @ 成员字段 |
| CLI 网关 `message/aibot/sessions/list`（Bot ID/Secret 签名换令牌） | 可用，已接入为 `GET /v1/bots/{id}/sessions`；依赖"可使用权限"授权（约 7 天），无到期时间查询接口 |
| CLI 网关 `chat/groups/list`、`chat/messages/list` | 错误码 853006"企业不可用"，读群消息仍需会话内容存档 |

修复：超限附件原回执提示"请重新发送"，重发仍会失败。现回执写明上限并提示压缩或拆分（`2f82899`），真机复测通过；
大小上限集中为 `MaxFileMBLimit` 与 `MaxMessageAttachmentBytes` 常量。
